# Deployment

This guide deploys the `examples/production` (or `examples/lab`) configuration into
an AWS account you have authenticated to. The repository is **not** applied
automatically; you drive every `plan` and `apply`.

> No live AWS deployment is performed by this repository. Review the plan and
> adapt the configuration to your organization before applying.

## 1. Prerequisites

- Terraform >= 1.6 (validated on 1.15.x), AWS provider ~> 5.0.
- An AWS account with permissions to create VPC, ECS, RDS, KMS, S3, IAM, and
  security-service resources.
- An ACM certificate (for the ALB HTTPS listener) in the target region.
- A container image in ECR (or another registry) that serves `GET /health` -> 200.
- Authenticated via the standard AWS credential chain - see
  [aws-authentication.md](aws-authentication.md).

## 2. AWS authentication

```bash
aws configure sso
aws sso login --profile zero-trust-prod
export AWS_PROFILE=zero-trust-prod
export AWS_REGION=ap-northeast-1
aws sts get-caller-identity
```

Alternative: AWS CLI profile, environment variables, an attached IAM role, or
GitHub Actions OIDC. No credentials are stored in the repository.

## 3. Backend configuration (remote state)

For production, store state remotely. Copy `backend.hcl.example` to
`backend.hcl`, replace the placeholders, and add a `backend "s3"` block to the
example's `terraform {}` block (see the snippet in `backend.hcl.example`), then:

```bash
terraform init -backend-config=backend.hcl
```

The state bucket must have versioning, SSE-KMS encryption, public access block,
and (recommended) a DynamoDB lock table. Bootstrap the bucket and lock table
separately first - see "Backend bootstrap" below. Do not hard-code the state
bucket name in the repository.

For a first local try you may omit the backend (local state) by running
`terraform init` with no `-backend-config`.

## 4. Variable setup

```bash
cd examples/production
cp terraform.tfvars.example terraform.tfvars
```

Edit `terraform.tfvars` to provide only non-secret configuration: AWS region,
project name, environment, VPC CIDR, availability zones, allowed ingress CIDRs,
ACM certificate ARN, container image, and RDS instance class. Do **not** put
access keys, secret keys, session tokens, passwords, or database passwords in
`terraform.tfvars`. RDS master credentials are generated by RDS and stored in
Secrets Manager automatically - you do not supply a database password.

## 5. Initialization

```bash
terraform init -backend-config=backend.hcl
```

## 6. Validation

```bash
terraform fmt -check
terraform validate
```

## 7. Plan review

```bash
terraform plan -out=tfplan
terraform show tfplan
```

Review every resource, especially IAM policies, security groups, and public
exposure. Do not apply until the plan matches your intent.

## 8. Apply

```bash
terraform apply tfplan
```

## 9. Verification

```bash
terraform output
aws ecs describe-services --cluster <cluster> --services <service>
aws rds describe-db-instances --db-instance-identifier <id>
```

Confirm the ALB responds over HTTPS and the `/health` endpoint returns 200.

## 10. Rollback

- ECS: redeploy a previous task definition (the service has a circuit breaker with
  rollback enabled).
- RDS: restore from the latest automated backup or a snapshot.
- Terraform: re-run `terraform plan` against the previous configuration version
  (use state versioning in the S3 backend) and `terraform apply`.

## 11. Destroy procedure

```bash
cd examples/production
terraform destroy
```

Then remove the S3 logging bucket, KMS keys (after their deletion waiting
period), and the remote state bucket/lock table if you no longer need them.

## 12. Production safeguards

- Use a remote S3 backend with versioning, encryption, and DynamoDB locking.
- Require pull-request plan review and a protected environment with manual
  approval before `apply` (see [github-oidc.md](github-oidc.md)).
- Use IAM Identity Center or OIDC; never long-lived access keys in CI.
- Keep deletion protection and Multi-AZ on for production (the production example
  defaults both on).
- Review CloudTrail, GuardDuty, and Security Hub findings after deploy.

## Backend bootstrap

Create the state bucket and lock table once, outside this repository, e.g.:

```bash
AWS_REGION=ap-northeast-1
STATE_BUCKET=<globally-unique-name>
aws s3api create-bucket --bucket "$STATE_BUCKET" --region "$AWS_REGION" --create-bucket-configuration LocationConstraint="$AWS_REGION"
aws s3api put-bucket-versioning --bucket "$STATE_BUCKET" --versioning-configuration Status=Enabled
aws s3api put-bucket-encryption --bucket "$STATE_BUCKET" --server-side-encryption-configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"aws:kms"}}]}'
aws s3api put-public-access-block --bucket "$STATE_BUCKET" --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
aws dynamodb create-table --table-name terraform-locks --attribute-definitions AttributeName=LockID,AttributeType=S --key-schema AttributeName=LockID,KeyType=HASH --billing-mode PAY_PER_REQUEST --region "$AWS_REGION"
```
